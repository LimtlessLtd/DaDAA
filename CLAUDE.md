# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Be concise and explicit in this file — no filler, no restating the obvious.

## What this is

Discord bot AI Dungeon Master: transcribes voice, feeds lore + session memory to an LLM, speaks replies back via TTS. World-building is entirely AI-generated (Session Zero + the DM inventing NPCs/locations/lore as play continues) — there is deliberately no external VTT (Foundry or otherwise) integration; don't reintroduce one.

## Run

No build/lint/test tooling exists (no `scripts` in package.json, no tests).

```
npm install
pip install -r requirements.txt
```

**One venv, Python 3.10-3.12** - Kokoro's phonemizer dependency (`misaki`) doesn't support Python 3.13/3.14 yet, and since Kokoro now lives in the same process as everything else (see Architecture below), that ceiling applies to the whole project, not just TTS. No separate `espeak-ng` system install needed - `misaki[en]` (a `kokoro` dependency) pulls in `espeakng-loader`, which bundles a prebuilt espeak-ng used for phonemizing invented fantasy names.

Then run a script in `startup_scripts/`. It starts 2 processes in order (each depends on the previous):
1. `server/core_server.py` — RAG HTTP (port 8766) + voice transcription WebSocket (port 8765) + TTS HTTP (port 8767) + image generation HTTP (port 8768) + the `docs/` lore-file watcher, all in one process (see Architecture below)
2. `node index.js` — bot + web dashboard, port 8000

Iterating on Node only: run `node index.js` directly if `core_server.py` is already up (bot degrades gracefully without it - see TTS fallback below).

Config: `config.json` picks the LLM (`OllamaConfig.enabled` = local Ollama, default; else `LLM` field for cloud). `.env` holds `DISCORD_BOT_TOKEN`, `BOT_OWNER_ID`, cloud keys. `README.md` is authoritative on current defaults (`qwen3.5:4b`) — `OLLAMA_SETUP.md` is stale (references `neural-chat`). Pin the tag, don't rely on the bare `qwen3.5` name: it resolves to `qwen3.5:latest` (9.7B), which on this deployment's 6GB-VRAM card only fits ~half in VRAM (`ollama ps` showed ~3.5/6.7GB resident) and silently falls back the rest to CPU - measured ~6.5 tokens/sec, vs `qwen3.5:4b` fitting entirely in VRAM at ~65 tokens/sec. Ollama gives no error when a model doesn't fit, just much slower inference, so check `ollama ps` during a real turn after changing models/hardware rather than assuming it fit.

## Architecture

```
Discord voice -> voice_manager.js -(opus, WS :8765)-> core_server.py [TranscriptionEngine: whisper+VAD]
             -> index.js (orchestrator)
             -> context_manager.js -(HTTP :8766)-> core_server.py [RagService: ChromaDB] [world lore lookup]
             -> ai_provider.js buildPrompt() -> callModel(): Ollama -> Gemini -> Anthropic -> OpenAI
             -> JSON reply {dialogue: [{speaker, voiceDescription, text}], suggestion, isOOC, isImportant, eventStatus, characterLogs}
             -> voice_manager.js speakText() per segment -(HTTP :8767)-> core_server.py [TtsService: Kokoro] -> Discord voice
```

- **Python side is 1 process, not 4** (`core_server.py`) — previously `rag_server.py`, `server.py` (whisper), `rag_ingest.py`, and `tts_server.py` were four separate scripts/processes across two Python venvs (Kokoro's phonemizer dependency, `misaki`, used to cap TTS at Python <3.13 while the rest of the project ran on a newer Python). All four are gone; the whole project now targets Python 3.10-3.12 (see Run above) and `server/core_server.py` is a single `aiohttp`-based process hosting RAG/transcription/TTS/image-generation on their own ports (8766 HTTP, 8765 WS, 8767 HTTP, 8768 HTTP) so **no Node-side code needed to change for the pre-existing three** - `context_manager.js callRagServer()` and `voice_manager.js`'s HTTP/WS clients still hit the same ports as before.
  - Each concern is a standalone class with no web-framework knowledge, under `server/services/`: `RagService` (ChromaDB + embedder), `TranscriptionEngine` + `VoiceSession` (faster-whisper/Silero VAD - engine is the shared expensive resource, session is cheap per-connection state, one per Discord user's WS connection), `TtsService` (Kokoro), `ImageGenService` (Stable Diffusion, see the dedicated bullet below), `DocsIngestService` (watches `docs/`, calls `RagService` directly now instead of over HTTP to itself as it did when it was a separate process).
  - Thin HTTP/WS adapters live under `server/web/` (`rag_routes.py`, `tts_routes.py`, `transcription_ws.py`, `imagegen_routes.py`) - they only translate requests into service method calls, no ChromaDB/Kokoro/whisper/diffusers knowledge. Blocking service calls (ChromaDB, Kokoro synthesis, Stable Diffusion generation) run via `loop.run_in_executor()` so they don't stall the WS connection sharing the same event loop.
  - `core_server.py` is just a composition root: constructs each service, wraps it in a route adapter, opens that service's `aiohttp` runner/port immediately (not batched at the end - see the `ImageGenService` bullet below for why this matters), constructing `ImageGenService` last.
  - `docs/` doesn't exist in this project, so `DocsIngestService` is currently a no-op at runtime (watches nothing) - kept so dropping static lore files in later works without code changes, same as before the merge.

- **index.js** is the orchestrator, not a thin entrypoint. `runDmTurn(transcript)` is the shared pipeline (build context -> call LLM -> react to reply); two call sites feed it: the `messageCreate` transcript handler (real speech) and `handleDiceMaidenRoll()` (fires after a tracked skill check resolves). `handleSilenceDriver()` is NOT a third one - it never calls the LLM at all (see the silence-driver bullet below). Don't re-duplicate `runDmTurn`'s logic for a new reactive trigger - extend it instead. Neither remaining call site calls `runDmTurn` directly - both go through `enqueueDmTurn()`, which chains calls onto a single module-level promise so turns run one at a time in trigger order. Without this, two triggers landing close together (e.g. a dice roll resolving while another player is mid-utterance) ran their LLM calls concurrently, and whichever HTTP response came back first queued its narration first - producing narration in the wrong order and letting a later turn's prompt be built from session state an earlier, still-in-flight turn was about to change. The one deliberate exception is Session Zero (`handleSessionZeroInput()`, below) - it bypasses `runDmTurn`/`enqueueDmTurn` entirely because it isn't a reactive DM turn, it's one-shot campaign generation with direct `speakText()` control over exactly what gets read aloud and when.
- **Real speech is debounced before it reaches `enqueueDmTurn`, the dice-roll trigger isn't**: Ollama (CPU) + Kokoro synthesis are slow enough that players often repeat themselves while waiting for a reply, but every `enqueueDmTurn()` call is a full serialized LLM+TTS turn - so 3-4 repeats used to queue up 3-4 slow turns back-to-back, making the wait longer with every repeat instead of shorter. The `messageCreate` transcript handler now calls `queueDmTranscript(sourceLabel, transcript)` instead of `enqueueDmTurn` directly: it buffers consecutive utterances arriving within `DM_TURN_DEBOUNCE_MS` (3s) of each other, then combines them into one turn (speaker-tagged `[source]: text` lines if more than one utterance was buffered, the raw single utterance otherwise) and calls `enqueueDmTurn` once. The moment that timer fires and a turn actually commits, it also plays a short pre-written filler line (`THINKING_FILLERS`, rotated round-robin) via `speakText()` directly - not through `runDmTurn`/`appendTranscript`, so it never touches session history - purely so players get audible confirmation they were heard before the real (slow) reply comes back. `handleDiceMaidenRoll()` still calls `enqueueDmTurn` directly since it's already a discrete one-off event with nothing to coalesce.
- **Silence no longer drives new narration, it just repeats the last line**: `handleSilenceDriver()` used to build a synthetic transcript ("Players are silent...") and run it through the full `runDmTurn`/LLM pipeline every 90s, prompting the model to invent something new. Replaced per request: it now fires every `SILENCE_TIMEOUT_MS` (5 minutes) and, if `lastSpokenTurn` (the `{speaker, text, voiceDescription}` segments from the most recent turn, captured at the end of `runDmTurn()`'s dialogue loop - deliberately not updated by one-off audio like `THINKING_FILLERS` or check announcements) is non-empty, just replays them verbatim via `speakText()` - no LLM call, no new content, and no `appendTranscript`/Discord post (it's a repeat, not new information, and re-logging it would duplicate the transcript/rolling summary). Keeps rescheduling itself every interval for as long as silence continues. Still a no-op during Session Zero/character intros (`isSessionZeroActive()`/`isCharacterIntroActive()`), same as before.
- **LLM output contract**: model must return one JSON object (shape in `ai_provider.js buildPrompt()`), including `checkCharacter`/`checkSkill`/`checkDc` (null unless a roll is being requested this turn). Local models emit malformed JSON often, so `ai_provider.js normaliseJson()` does defensive repair (strip code fences, fix smart quotes/Python literals, brace-scan, `Function()` eval fallback, flatten nested objects). Trust that function, not raw output. Because `flatten()` merges any nested object's keys straight into the top level (destroying the parent key), new LLM fields must stay flat, not nested - `dialogue`/`characterLogs`/`worldEntities` are arrays, which `flatten()` leaves untouched (it only recurses into plain objects), so their per-item shape is safe to nest.
- **Narration is multi-speaker, not one flat string**: the reply's `dialogue` array (guideline 5) is a sequence of `{speaker, voiceDescription, text}` segments read aloud in order, so one turn can narrate AND voice an NPC's line, each in its own voice - `index.js runDmTurn()` loops the array, calling `speakText(segment.text, segment.speaker, segment.voiceDescription)` and `appendTranscript()` per segment. `speaker` is `"narrator"` or the exact NPC/character name; `voiceDescription` (free text, e.g. "gruff old male dwarf, deep and gravelly") only matters the first time that name is ever used - see TTS below for what happens to it. Every segment also gets a matching `postToActiveChannel()` Discord post (an NPC's line always includes their portrait when one exists, see the image-generation bullet below; a narrator line posts plain text) - by design, real narrative content spoken via `speakText()` always has a text counterpart in Discord. The two deliberate exceptions are non-narrative audio that was never meant to touch session history either: `THINKING_FILLERS` (queueDmTranscript()'s "one moment" filler while a turn is still in flight) and `handleSilenceDriver()`'s repeat of `lastSpokenTurn` (see below) - the latter would just re-post the same text that was already posted the first time, every `SILENCE_TIMEOUT_MS`, for as long as the table stays quiet.
- **Narrator persona/tone is generated once per campaign, not re-invented per turn**: `ai_provider.js generateCampaignSeed()` returns a `narratorPersona` field alongside `introLore` (a couple of sentences on this campaign's narrative voice/pacing, inferred from the players' Session Zero ideas) - `handleSessionZeroInput()` persists it into `campaign_intro.json` next to the intro text. Every later `runDmTurn()` call re-reads that same file (same "small file, read fresh every turn, no cache to invalidate" pattern as `current_event.json`) and passes it into `buildPrompt()`'s `narratorPersona` param, which renders it near the top of the prompt plus guideline 14 telling the model to keep narrating in that voice - since each LLM call is otherwise stateless with no memory of "how it's been talking" across turns. Blank/missing (pre-Session-Zero, or a freshly wiped campaign) is handled the same as any other optional context string - the section and cross-reference simply don't render. Surfaced read-only on the dashboard's World Setting panel above the intro text.
- **Dice roll matching** (the trickiest part): a check request sets a pending entry (`check_manager.js`, one per character, `temp_data/pending_checks.json`). `messageCreate` special-cases Dice Maiden's bot messages (`src/dice/dice_maiden.js isDiceMaidenMessage()`, tag configured via `config.json DiceMaidenTag`) before the normal "ignore bots" guard, parses the roll total via regex (`parseDiceMaidenRoll()` - only trusts the trailing `= <total>`, not bracket contents, since modifiers vary; strips Discord markdown `**`/`` ` `` first since Dice Maiden's real replies are bold/code-formatted, e.g. `` Roll: `[8]` = **8** ``), then attributes it to a player via Discord interaction metadata first, falling back to Dice Maiden's printed display name resolved through a nickname->username map (`character_manager.js recordDiscordNickname`/`resolveUsernameByNickname`, `temp_data/discord_nicknames.json`) - necessary because Dice Maiden shows the server nickname, not the account username that `character_map.json` is keyed on. Nicknames are captured opportunistically whenever a bound player's voice is transcribed. `isDiceMaidenError()` filters out Dice Maiden's own "invalid expression" replies so those aren't logged as parse failures.
- **Ollama context window is set explicitly, don't drop it**: Ollama defaults `num_ctx` to 2048 regardless of what the model actually supports, and the DM prompt's static schema+guidelines alone already run ~2.5k tokens before any world context/history/transcript is added - realistic mid-session prompts measured around ~3.9k tokens, so without an explicit override every request was silently truncated before the model saw most of its own instructions (likely the real cause behind a lot of the "model ignores guideline X" issues patched elsewhere in this file). `ai_provider.js callOllama()` now passes `options.num_ctx` from `config.json OllamaConfig.numCtx` (currently `16384`) - Phase 6 benchmarked this on the actual deployment hardware (RTX 2060 6GB) rather than leaving the original `32768` (chosen for "generous headroom" without a documented benchmark) unexamined. Every prompt section that could otherwise grow over a session is already capped in code (8 RAG records, last 15 player logs, a 2000-char rolling summary that self-condenses), so a padded ~5.2k-token stress-test prompt is close to the real ceiling, not just today's ~3.9k-token measurement - `16384` leaves ~2x that ceiling in headroom while measuring only ~5% slower token generation than `8192`, comfortably ahead of `32768`'s ~19% slowdown for no accuracy benefit. Also sets `keep_alive: -1` on every request so a lull (including the silence-driver's own interval) never forces a full reload-from-disk on top of normal inference time. If you change models/hardware, or prompts grow substantially (more world records, longer rolling summary), re-run the comparison rather than assuming `16384` still fits - `numCtx` is the knob to retune, not the prompt wording.
- **Provider fallback**: Ollama first if enabled, else/on-failure `fallbackToCloudProviders()` tries Gemini -> Anthropic -> OpenAI based on which `.env` key exists and matches `config.LLM`. `ai_provider.js selectCloudProvider()`/`callCloudProvider()` are the shared provider-selection helpers - every new LLM-calling function (there are three: `callModel`, `generateNextEvent`, `generateCampaignSeed`) should reuse these rather than re-duplicating the key/provider matching logic. Similarly, `parseJsonLoose()` (robust cleanup, no flattening) vs `normaliseJson()` (`parseJsonLoose` + `flatten()`) - use `parseJsonLoose` when the expected shape has meaningful nesting you need to keep (like `generateNextEvent`'s `{activeEvent: {...}}`), `normaliseJson` when the shape is flat-or-arrays-only (the main DM schema, `generateCampaignSeed`'s `{introLore, worldEntities: [...]}`).
- **World knowledge is AI-generated, not imported**: `data_manager.js` loads structured entities from `temp_data/<type>/*.json` (npcs/locations/items/quests/lore/encounters); everything - including entities the DM invents mid-session - lives in a **single** ChromaDB collection, `dnd_knowledge` (tagged with a `type` metadata field, not split per category). This is deliberate: `findRelevantRecords()` (the function that actually feeds every prompt) only ever queries `dnd_knowledge`, so anything synced anywhere else would be invisible to the DM - don't reintroduce per-category collections without also updating `findRelevantRecords()`. `context_manager.js syncKnowledgeToRAG()` does the bulk sync at startup; `context_manager.js addWorldEntities()` is the incremental path - called from `runDmTurn()` whenever the LLM reply includes a `worldEntities` array (guideline 11 in `ai_provider.js`), it dedupes against already-known names (`exactNameCache`) before calling `data_manager.js saveEntity()` and pushing straight into `dnd_knowledge`, so newly-invented lore is queryable on the very next turn without a restart. `DocsIngestService` (in `core_server.py`) separately watches `docs/` for static lore files, but that folder doesn't exist in this project - it's currently a no-op, not a bug, just unused.
- **Entities can be `secret: true`**: background lore/NPCs/locations the DM knows but hasn't revealed to players. Guideline 11 tells the model to set this when inventing something not yet public, and to never state a Record tagged `[SECRET]` (added by `runDmTurn`'s `contextString` formatting in `index.js`) directly to players - only let it surface through play.
- **Session Zero is one flow, voice-driven end to end** (there used to be two - a dead one in `ai_helper.js` that was never wired up, and a synchronous one that generated before asking players anything - both removed). Sequence:
  1. Dashboard "Start New Campaign" -> `web_editor.js /api/start_campaign`: wipes RAG collections, session-scoped files (including `character_map.json`/`character_logs.json`), all stored entities (`data_manager.js clearAllEntities()`), and the in-memory world cache (`context_manager.js resetWorldCache()` - without this the cache would still serve deleted entities until a restart). Then calls `session_manager.js startSessionZero()`, which speaks a fixed prompt asking players for world ideas (also posted to the Discord text channel via `image_gen_manager.js postToActiveChannel()`, so it isn't voice-only), and returns immediately - it does **not** generate anything itself.
  2. While `isSessionZeroActive()` is true, `index.js`'s transcript handler routes every utterance to `handleSessionZeroInput()` instead of `runDmTurn()` - buffered via `addSessionZeroInput()`, not reacted to as in-character speech. `handleSilenceDriver()` also no-ops while active, so the silence-repeat timer doesn't interrupt brainstorming.
  3. `handleSessionZeroInput()` checks each utterance against `SESSION_ZERO_FINISH_REGEX` (a completion-phrase detector - note contractions need `('re| are)` as one alternation, not `(are|'re)`, since `"we're"` has no space before `'re`). It accepts several equivalent phrasings, but players were never actually told any of them - both `SESSION_ZERO_PROMPT` and `CHARACTER_INTRO_PROMPT` (`session_manager.js`) now explicitly say `say "we're done" when you're finished`, so it's no longer a guessing game which words actually end the phase. On match: `endSessionZero()` returns the compiled ideas, which get passed to `ai_provider.js generateCampaignSeed(playerIdeas)` - a one-shot LLM call producing `{introLore, narratorPersona, worldEntities}` built on what the players actually said. The intro lore is saved to `dnd_knowledge`, spoken aloud via `speakText()`, and posted to Discord via `postToActiveChannel()`; `narratorPersona` is saved into `campaign_intro.json` alongside it (see the dedicated bullet below); the entities (public and secret) go through `addWorldEntities()`; then, instead of jumping straight to the opening event, `handleSessionZeroInput()` stashes the intro lore in the module-level `pendingCampaignIntroLore` and calls `session_manager.js startCharacterIntros()` to hand off to step 4.
  4. Character introductions - a second buffered phase, structurally identical to Session Zero itself (`isCharacterIntroActive()`/`addCharacterIntroInput()`/`endCharacterIntros()` in `session_manager.js`, same `SESSION_ZERO_FINISH_REGEX` completion detector, `handleSilenceDriver()` also no-ops while it's active): `startCharacterIntros()` asks each player, in turn, for their name, their character's name, a brief description, and what that character is doing as the scene opens (also posted to Discord via `postToActiveChannel()`, same as `startSessionZero()`'s prompt). `index.js`'s transcript handler routes to `handleCharacterIntroInput()` while this phase is active. On the finish phrase, `endCharacterIntros()` returns the compiled transcript, which goes to `ai_provider.js parseCharacterIntroductions()` - a one-shot LLM call extracting one `{discordUser, characterName, description, openingAction}` per player heard. `beginSessionOne()` then binds each pair via `character_manager.js bindCharacter(discordUser, characterName)` (this is what makes Discord user -> character mapping automatic instead of requiring manual dashboard binding), logs each character's opening description via `addCharacterLogs()`, and folds all of it into a single `openingContext` string.
  5. `beginSessionOne()` calls `generateNextEvent()` with `pendingCampaignIntroLore` and `openingContext` (a new optional 4th parameter, empty string for the regular per-turn call site in `runDmTurn()`) so the opening event can react to where each character actually said they were, not just the campaign's intro lore. The result is written to `current_event.json`, spoken aloud, and posted to Discord.
- **Event state machine**: `temp_data/current_event.json` holds one `activeEvent` + `archivedEvents[]`. Reply's `eventStatus` drives it: `resolved` archives + calls `generateNextEvent()`; `escalated`/`evolved` mutates `complication` in place. Every status change (`resolved`/`escalated`/`evolved`, never `stable`) also gets a text-only `index.js announceEventStatusChange()` post to Discord, deliberately independent of `enqueueEventImage()`'s async image job (which can fail, be disabled, or just not have finished yet) - includes a `kind: 'new'` case for the freshly-generated next event after a resolve, since that event's own description is never otherwise spoken aloud (it's produced by a separate, later `generateNextEvent()` call, not narrated in the turn that resolved the old one). `activeEvent.description` is fixed flavor text written once when the event is created - it never gets edited, so a separate `activeEvent.currentState` field carries whatever `resolutionSummary` the model reports each turn, updated regardless of `eventStatus` (including `stable`) and fed back into the next prompt as overriding `Description` wherever they conflict. Without this, concrete scene changes (an item taken/destroyed, an NPC killed) on a `stable` turn would be silently dropped and the stale `Description` would contradict them on the next turn.
  - Guideline 11 (`ai_provider.js buildPrompt()`) spells out that a diplomatic/creative attempt which hasn't succeeded *yet* is `stable` or `evolved`, never `escalated` by default - models otherwise default to "the situation escalates" as a safe-seeming answer whenever players don't resolve the obstacle outright, even when what they actually did was open a negotiation. There's no code-level backstop for this (unlike the DC-announcement one below) - detecting "is this attempt diplomatic" reliably needs real judgment, not a keyword match, so this is prompt wording only and depends on the model actually following it.
- **Background events run independently of the current event, on their own slow cadence**: `src/sessions/background_event_manager.js` is a `check_manager.js`-style file-backed store (`temp_data/background_events.json`) for concurrent narrative threads (a cult gathering, a rival party's progress, a political feud) that escalate/resolve on their own, separately from the single "current event" above - unlike the current event, players may never learn of most of them (`secret: true` by default). They are **not** injected into the main per-turn `buildPrompt()` at all - "current event" stays purely about the immediate situation, per its own name. Instead, `index.js`'s utterance handler increments a second counter (`backgroundEventCounter`, alongside the existing `transcriptCounter` that drives `updateRollingSummary()`) and fires `updateCampaignBackgroundEvents()` every `config.json BackgroundEventConfig.utteranceInterval` (default 25) utterances - deliberately less frequent than the rolling-summary refresh, since these are meant to be occasional. That calls `ai_provider.js updateBackgroundEvents()`, a one-shot LLM call explicitly framed as change-averse ("most threads should NOT change most of the time"), returning `{ updates: [...], newThread: {...}|null }` - nested, so parsed with `parseJsonLoose` like `generateNextEvent`, never `normaliseJson`. `background_event_manager.js applyBackgroundEventUpdates()` applies it: matches `updates[]` entries to existing threads by `id`, and only accepts a `newThread` while under a hard code-level cap (`MAX_ACTIVE_THREADS = 4`) - a deterministic backstop on top of the prompt's "propose at most one, rarely" wording, same pattern as `MAX_ROLLING_SUMMARY_CHARS`. No image generation and no Discord posting for these - either would leak a "secret" thread to players.
  - **Tying new events to what already exists**: `generateNextEvent()` (`ai_provider.js`) takes an optional 5th `tieInContext` param - `background_event_manager.js buildEventTieInContext(activeThreads, records)` formats the active background threads plus a handful of already-established world-entity records into one block, told to the model as material it should prefer weaving into the new event over inventing an unconnected cast from scratch. All three call sites pass this: the automatic "event resolved -> generate next" path in `index.js runDmTurn()` (reusing `relevantRecords`, the same RAG-queried records already fetched for that turn's main prompt - no extra RAG call), `beginSessionOne()`'s opening-event generation, and the dashboard's manual "Generate new event" button (`web_editor.js /api/generate_event`). If the model ties the new event to a specific background thread, it sets `linkedBackgroundEventId` in its response; all three call sites then call `resolveBackgroundEventAsSurfaced()`, which marks that thread `resolved` and flips `secret` to `false` - it stops being a background thread the moment it becomes the thing players are actually facing.
  - Dashboard surfaces active (non-resolved) threads read-only in a "Background Threads" sub-section of the existing Current Event panel (`GET /api/session_state`'s `backgroundEventsData`, same bolt-on-the-response pattern already used for `currentEventData`) - DM-only visibility, same "SECRET" badge convention as the World Entities panel, never posted anywhere players can see it.
- **Check announcements are enforced in code, not just prompted**: guideline 6 in `ai_provider.js` asks the model to state the skill/DC out loud in a `dialogue` segment, but it doesn't always comply. `index.js announceCheckRequirement()` runs unconditionally whenever `addPendingCheck()` registers a check, speaking a deterministic `"<Character>, make a <Skill> check - you need to beat a DC of <DC>."` line (and posting it to Discord) regardless of what the narrative said - a guaranteed backstop, not a replacement for the prompt guideline. `announceOpenGroupCheckRequirement()` is the same for group checks.
- **TTS voices are dynamic per character, not a fixed enum**: the narrator's voice is fixed (`bm_george`), but every other speaker's voice is derived from the LLM's free-text `voiceDescription` (e.g. "gruff old male dwarf") and then locked in - `src/voice/voice_registry.js resolveSpeakerVoice(speaker, voiceDescription)` is the source of truth: first time a speaker name is seen, `deriveVoiceFromDescription()` keyword-matches gender/age/texture words in the description to pick a gender pool (`MALE_VOICES`/`FEMALE_VOICES`, 4 voices each - `bm_george`/`bm_lewis`/`bm_daniel`/`bm_fable` and `bf_emma`/`bf_isabella`/`bf_alice`/`bf_lily`, the entirety of Kokoro's British English catalog), hash-selects 2 of that pool's 4 voices, blends them with a description-derived weight, plus a speed nudge, and persists the result to `temp_data/character_voices.json`; every later turn for that name reuses the stored blend regardless of what `voiceDescription` says (or whether it's given at all) - this is what makes "same character, same voice all campaign" work. `server/services/tts_service.py TtsService.KNOWN_VOICES` must list the same 8 voices so they're all pre-loaded at startup (see below) - a voice missing from that list still works, it just pays a one-time Hugging Face download on first use instead of being warm. This is a deterministic approximation (finite blend space from keyword matches), not a literal generative rendering of the description - a real natural-language-conditioned TTS model (e.g. Parler-TTS) was ruled out for being too slow on CPU. `character_voices.json` should be wiped alongside the other session-scoped files on "Start New Campaign" (`web_editor.js /api/start_campaign`) so voices don't leak between campaigns.
- **TTS transport**: `voice_manager.js speakText(text, speaker, voiceDescription)` resolves the voice via the registry above, then posts `{text, voices: [{name, weight}], speed}` to `core_server.py`'s TTS route (port 8767) - `TtsService`'s Kokoro pipeline is loaded once at process startup so per-line synthesis stays fast, a fresh process per line would re-pay Kokoro's model load cost every turn. The route/service has no notion of characters or profiles - it just blends the given named voice tensors by weight (`PIPELINE.load_voice(name)`, weighted average) and synthesizes; all voice-assignment logic lives in Node. If `core_server.py` is unreachable, `voice_manager.js` falls back to spawning `local_tts.py` (legacy gTTS/pyttsx3, collapsing the blend down to a coarse male/female/narrator guess) - lower quality, but keeps the bot speaking during setup.
- **Fixed lines are pre-synthesized, not re-synthesized on every use**: `THINKING_FILLERS` (index.js) and the Session Zero/character-intro prompts (`session_manager.js`'s exported `SESSION_ZERO_PROMPT`/`CHARACTER_INTRO_PROMPT` constants) are exact, unchanging text spoken as `"narrator"` - a fixed voice (`NARRATOR_VOICE` in `voice_registry.js`, no per-description derivation), so the same text always synthesizes to the same audio. `voice_manager.js pregenerateStaticAudio(lines)` synthesizes any of these not already cached and writes them to `tts_cache/` (project root, git-ignored, NOT under `temp_data/` since this cache is campaign-independent and must survive "Start New Campaign") keyed by a sha1 hash of the exact text; `index.js`'s `clientReady` handler calls it once at startup with all of them combined, best-effort (a failure just means that line falls back to normal dynamic synthesis the first time it's actually spoken, same as if pre-generation had never run). `processTtsQueue()` checks this cache before ever hitting `core_server.py` - only for narrator-voiced items, since the cache only ever contains narrator lines and an NPC line coincidentally matching one verbatim would still be wrong to play in the narrator's voice. Idempotent by design (skips a line whose hash is already on disk), so calling it every startup is cheap and correct. If you add a new fixed narrator line elsewhere, add it to the list passed to `pregenerateStaticAudio()` in `clientReady` or it'll just always take the slow dynamic path.
- **Image generation (every world entity type + event scenes) never blocks anything else** - `server/services/image_gen_service.py ImageGenService` is a "dumb" prompt-in/PNG-out Stable Diffusion (`stabilityai/sd-turbo` by default, overridable via `IMAGEGEN_MODEL` env var) wrapper, exactly like `TtsService` - no entity/event/Discord/rate-limit awareness. All of that orchestration lives in Node, in `src/images/image_gen_manager.js`, which mirrors `voice_manager.js`'s `ttsQueue`/`processTtsQueue()` pattern (push + fire-and-forget dispatch, re-entrancy guarded by a boolean checked synchronously before the first `await`) with a time-based rate gate (`config.json ImageGenConfig.minIntervalMs`, shared across **all** job kinds so a burst of entities/event changes can't hammer the image server at once) and a hard kill switch (`config.json ImageGenConfig.enabled` - `enqueueEntityImage()`/`enqueueEventImage()` both no-op immediately when `false`, defaulting to `true` via `!== false` so an older config.json without the field still works). Callers never `await` a job.
  - **Runs on CPU by default (`IMAGEGEN_DEVICE=cpu`, set in both `startup_scripts/` scripts), not GPU**: on a 6GB card this shares with Ollama, just having Stable Diffusion resident measurably slowed every LLM turn - benchmarked `qwen3.5:4b` dropping from ~65 tok/s to ~25 tok/s purely from Kokoro+SD sitting in VRAM, worse still if a render is actively running when a turn starts (nothing synchronizes `enqueueEntityImage`/`enqueueEventImage` with `runDmTurn()`, so they can and do overlap). Since image posts are already fire-and-forget and rate-limited, trading their speed away for the LLM's is a clean win on hardware this size - remove the env var (or set it to `cuda`) if you have a card with room for both.
  - **Triggered by what actually comes up in play, not by invention** - `context_manager.js addWorldEntity()` (called whenever the LLM's `worldEntities` array introduces something new, guideline 10) deliberately does NOT enqueue an image; inventing an entity isn't the same as it being "new to" the players, especially for `secret` background lore they may never encounter. The only two triggers are inside `index.js runDmTurn()`'s dialogue loop: (a) an NPC actually speaking (`speaker` != `"narrator"`) enqueues an image for that NPC via `getEntityByName(speaker)`, with a backstop that auto-registers a minimal `npcs` entity (via the now-exported `context_manager.js addWorldEntity()`, best-effort description built from that line's `voiceDescription`) the first time a speaker has no entity record at all - guideline 10 isn't always followed, so without this an NPC could talk the whole campaign and never become image-eligible; and (b) `context_manager.js findMentionedEntities()` scans every segment's text (narrator included) for a substring match against any other already-known entity's normalized name (same index `getEntityByName()` uses) and enqueues/posts for whichever ones it finds - e.g. narration describing a location or item the party just found. Case (a) posts text-only (with a light re-enqueue retry) when no image exists yet, since it's already posting the NPC's line regardless; case (b) only posts when an image already exists (a passing mention isn't reason enough to spam a text-only post per mention while art generates), otherwise it just enqueues silently for next time. `ENTITY_IMAGE_STYLE` in `image_gen_manager.js` gives each entity type (npcs/locations/items/quests/lore/encounters) its own prompt framing and aspect ratio - a bust-shot portrait style makes no sense for a location or quest emblem.
  - Images are generated once and locked in forever via `src/images/entity_image_registry.js` (`temp_data/entity_images.json`, keyed by normalized entity name - the same "generate once, reuse all campaign" pattern as `character_voices.json`, deliberately re-implementing the one-line name normalization rather than importing `context_manager.js`'s `normalizeText` to avoid a require cycle, since `context_manager.js` used to require `image_gen_manager.js` - it no longer does, now that `addWorldEntity()` doesn't enqueue images itself, but the registry still keeps its own copy rather than reintroducing that dependency).
  - Event images: `index.js`'s event-status-change handling fires `enqueueEventImage(activeEvent)` for `escalated`/`evolved`/`resolved` (never `stable`), and `beginSessionOne()` fires it once more for the very first opening event (Session Zero -> Session 1 handoff) so the campaign's opening scene gets an image too, not just later transitions. Event images always overwrite the same file (`temp_data/event_images/current_event.png` - only one event is ever active) and a newer queued event-image job drops any older still-queued one for the same reason (debounce to latest, not one post per transition) - a job already in-flight can't be cancelled and still completes/posts. `enqueueEventImage()` also tracks a signature (title + `currentState`/`description`) of the last queued/generated event image and skips enqueueing entirely when a status change (escalated/evolved) didn't actually alter that text (e.g. a turn with no `resolutionSummary`) - otherwise every escalate/evolve would burn a generation slot on a picture identical to the one already posted. Event image posts are captioned with the event's current state/description.
  - `postToActiveChannel()` needs a live `TextChannel` reference to post into, which nothing in this codebase persisted before this feature - `index.js`'s `!join` handler calls `setActiveTextChannel(message.channel)` the moment voice is joined, mirroring how `voice_manager.js` holds onto `currentVoiceConnection`. `core_server.py` constructs `ImageGenService` **last** and opens each service's port immediately after constructing it (not batched at the end like before) specifically so a slow first-run Stable Diffusion model download can never delay RAG/transcription/TTS becoming reachable.
- **Session memory**: `ai_helper.js` keeps a rolling text summary (`temp_data/ai_memory.json`), refreshed by an LLM call every 10 utterances. `character_manager.js` maps Discord users -> character names (`temp_data/character_map.json`) + per-character/per-player logs. All of this gets injected into every prompt.
  - `updateRollingSummary()` normally asks the model to "update" the existing summary (append new events on top) - a soft prompt instruction to "keep it brief" that a local model isn't guaranteed to actually follow over a long session, unlike the rest of `buildPrompt()`'s context sections which are all bounded in code (World Context: 8 RAG records x 300 chars max; Player Logs: last 15 entries; Current Event: one object). Once `memory.rollingSummary` exceeds `MAX_ROLLING_SUMMARY_CHARS` (2000), the next refresh switches to a different prompt that asks the model to condense it from scratch (target: well under 1000 chars) instead of extending it further - a deterministic backstop against unbounded growth, same pattern as `announceCheckRequirement()`.
- **Web dashboard** (`src/web/web_editor.js`, port 8000, static `dashboard.html` alongside it in `src/web/`): CRUD API over world entities/character bindings, plus a live view of `temp_data/llm_debug.json` (overwritten on every LLM call) — fastest way to inspect prompts/replies without Discord running. `/api/refresh` re-syncs world data from disk into RAG and the in-memory cache without a restart (dashboard's "Refresh World Data" button, Debug & RAG tab).
  - **Performance tab** (`GET /api/telemetry`, backed by `src/telemetry/telemetry_manager.js`): the per-stage latency breakdown that Phase 6 added as a console log (`index.js` "Turn latency breakdown", `voice_manager.js` STT timing) is also persisted to a bounded rolling history (`temp_data/telemetry_turns.json`/`telemetry_utterances.json`, last 200 entries each — telemetry never feeds a prompt, so this is capped purely to bound file growth, not a token budget) so the dashboard can chart trends instead of only the latest value. The tab also surfaces a live snapshot of in-flight work pulled fresh on every poll: TTS queue depth (`voice_manager.js getTtsQueueStatus()`), image-gen queue depth (`image_gen_manager.js getQueueStatus()`), pending dice checks, open group check, active background event count, and whether a DM turn is currently running (`index.js` pushes this last one via `registerLiveStatusProvider()` at startup, mirroring `setActiveTextChannel()`'s push-state-in pattern — needed because `telemetry_manager.js` is required by `web_editor.js`, which `index.js` requires, so `telemetry_manager.js` requiring `index.js` back for its module-level state would be circular). Stage colors (STT/RAG/LLM/reply-to-audio) are a fixed, colorblind-validated categorical set reused across every chart on the tab so the same color always means the same stage.
- **Any endpoint that clears world/RAG state must also call `resetWorldCache()` and `voice_manager.js stopSpeaking()`**: `/api/start_campaign` and `/api/rag_clear` both wipe RAG collections and/or stored entities - without `resetWorldCache()`, `context_manager.js`'s in-memory `worldDbCache`/`exactNameCache` keep serving the deleted entities until a restart; without `stopSpeaking()`, whatever's still in `voice_manager.js`'s `ttsQueue` (a DM turn can queue several `dialogue` segments at once) keeps playing right through the reset, sounding like the DM is still mid-conversation from the old campaign. `/api/start_campaign` similarly calls `image_gen_manager.js clearImageQueue()` and deletes everything under `temp_data/entity_images/`/`temp_data/event_images/` (plus resetting `entity_images.json`) - otherwise an entity/event-image job still mid-flight for the old campaign could land and get posted/persisted after the reset.
- **Half-built, unreachable features get deleted, not left around**: session notes/reminders (a trigger-phrase reminder system with full CRUD + matching logic, but no dashboard UI ever created one and triggered notes were never actually fed into the prompt), the "relationships" subsystem (NPC/location link tracking - same story: full CRUD + a migration function, zero UI, and its only consumer `buildDmSuggestion()` was itself never called), the old record search/browse endpoints (`/api/records`/`/api/categories`/`/api/record`, superseded by RAG-query search + the World Entities panel), and `/api/purge` (subsumed by `/api/start_campaign`) were all removed for this reason. If you're adding a feature with both a storage layer and an API, wire up the UI in the same change - don't let a third half-built one accumulate.
- **Storage**: flat JSON (plus generated portrait/event-image PNGs) under `temp_data/` + ChromaDB in `chroma_db/`, both git-ignored, both are per-campaign save state. Clearing both resets the world; they're independent stores.
